# 从研究主题到实际结果与论文

当用户委托自行做实验，执行者负责选题、实现、运行、分析和成稿。沿用用户工作项目的代码和数据约定。新课题可使用一个研究目录存放方案、版本化代码、按运行分开的原始输出、分析脚本和稿件。实验产物写入用户的研究目录，技能安装目录用于读取工具和规则。

## 把创新性变成可以检验的研究问题

1. 从用户给出的对象确定**决策变量、可观测信息、决策时机和目标**。例如 NoC 中“任务调度”可能指 DAG 任务到核的映射及执行顺序、源端对就绪通信流的注入次序，或路由器对输出端口的仲裁。对象明确是流量时，可以先选源端注入顺序，说明这一选择。若结论要论及应用完成时间，就须另外实现任务依赖、执行时间和数据到达约束。
2. 用 [检索协议](literature-search.md) 查最近且对象相同的工作，记录检索日期、查询式、已读出处及所用假设。逐一比较决策位置、输入信息、竞争模型、计算预算和指标。在改变选题前先查能削弱创新主张的工作。已有研究把局部搜索与遗传算法用于考虑争用的 NoC 映射与调度；再用一次 GA 或换成 ACO 本身不足以建立贡献。[Yan 等，ICAPS 2020](https://cdn.aaai.org/ojs/6675/6675-40-9904-1-10-20200521.pdf)
3. 提出候选机制及其可能失效的场景。例如检验“将共享链路的就绪流错峰后，拥塞负载下的整批完成周期能否缩短，低竞争时多付多少等待或搜索开销”。这是一条待验证假设。选择简单可解释的策略、相近领域方法和能单独移除该机制的对照。搜索算法比较同时报告目标评估次数、可获得的信息和求解耗时。小实例可用穷举最优解校验实现或估计差距。
4. 在看最终结果前写下研究问题、主指标与单位、实验单位、工作负载、对照、随机化/配对、预算、停止条件及反例。先区分比较、因素筛选和优化目标，再选择设计与重复方式。把协议落在 [实验方案](../templates/experiment-plan.md) 或项目已有配置里。[NIST 实验设计选择](https://www.itl.nist.gov/div898/handbook/pri/section3/pri33.htm)
5. 用户指定“SCI B 类”时，先用目标读者和贡献类型指导实验。标记机构、学科、目录版本为待匹配，获得适用目录后再核候选刊及稿约。当前研究可继续。最终分别给出已证实的差异、仍需验证的新意，以及决定投稿适配性的证据。

若预跑显示简单策略已取得同样收益，检查拥塞发生在哪条链路、决策时有哪些信息，以及比较是否能区分候选机制。根据文献差异和失败原因决定是否改设计，并注明新假设、增补对照和所需预算。若已查看过正式测试结果，再据此改方法，应保留首轮结果，另取独立留出数据验证修订后的方法。预算只够评估原设计时，如实写出已检验的贡献与未解问题。

## 执行前查看真实环境

已有数据的统计、AI 训练与推理选择 [数据分析](data-analysis.md) 中的执行规程。无论使用何种计算后端，正式运行结束后按该文从原始记录重建比较。

先读项目环境文件，在实际运行节点、用正式命令将使用的解释器和启动选项检查资源与依赖。已有 WSL、容器或服务器模块可在对应环境复验。探针可实际执行 NumPy 运算、指定 Torch 设备的反向计算或 Icarus 编译仿真。接着跑一次有已知答案的项目输入，估计用时、内存、存储和可承担的实验规模。[后端验证与环境修复](compute-environment.md)

普通依赖缺失时在项目隔离环境内安装，再用同一操作复验并继续。用户要求提前告知时先说明缺什么、安装位置和用途。若明确要求等确认，按其要求处理。涉及系统驱动、重启、商业许可证、付费或服务器权限时，说明受影响的实验、失败命令、用户所需的最小操作和复验命令，先完成其余可运行的部分。

## 从小样例到正式运行

做离散事件/NoC 仿真、HDL 编码或数字逻辑功能验证时，按[仿真与 HDL 实验](simulation-and-hdl.md)检查模型语义及 DUT 对外接口。做连续系统数值仿真时，按[解析基准和离散化误差检查](experiment-design.md#连续数值仿真)校验求解器。数据问题和模型训练、推理按[数据分析](data-analysis.md)选择实验单位及划分。

1. 为基线和候选方法编写可执行实现。先用手算、小规模穷举或独立参考模型核对已知输入，加入一个能暴露真实错误的反例。数值或协议不符时先修实现，再用新运行标识重跑。保留旧的失败记录。
2. 执行小规模预跑，检查输出结构、正确性、运行时间和资源。保存正式矩阵及其工作负载/种子清单。需要跨方法、参数或独立种子多次运行时，按[矩阵执行与接续](experiment-matrix.md)传入每个单元的实际参数，失败后只补受影响的单元。调整模型、代码或评价规则时留下变更理由，注明哪些旧结果仍可比。
3. 以项目的复现实验框架或 [前台运行记录工具](../scripts/run_experiment.py) 执行。下例从研究项目根目录启动，读取该项目的 `src/simulate.py` 和 `config.json`。按[平台说明](platforms.md)替换解释器和技能路径，保留带引号的 `{python}`，让仿真沿用启动工具的解释器。

   ```text
   python "<技能目录>/scripts/run_experiment.py" --cwd . --run-dir runs/trial-01 --input src/simulate.py --input config.json --output runs/trial-01/metrics.csv -- "{python}" src/simulate.py --config config.json --output runs/trial-01/metrics.csv
   ```

   将参数换成项目的真实命令和路径，明确指定选好的环境解释器。每次重试用新目录。记录代码版本或摘要、配置、环境、参数、输入标识、种子、日志、退出状态和原始输出。工具记录子进程及文件，执行者另核行数、覆盖率、数值范围和实验断言。退出成功但零条测量、断言失败或缺少预期对照时，不进入正式结果。
4. 使用已获准的服务器和调度系统时，提交前确认工作目录、账户配额和输出位置。Slurm 普通 `sbatch` 返回作业 ID 后，继续检查队列与作业终态，例如 `squeue -j JOBID`、`sacct -j JOBID --format=JobID,State,ExitCode,Elapsed`。检查具体步骤的退出码、日志和产物。作业在队列中消失须核对终态。数组作业核对每个条件与索引，记录超时、抢占和失败，只重跑受影响的单元。无记账服务时用该站点可用的等价状态与产物检查。交付前持续跟踪已接受的任务直至完成或遇到需用户解决的具体依赖。[Slurm 提交作业](https://slurm.schedmd.com/sbatch.html) · [退出状态](https://slurm.schedmd.com/job_exit_code.html)

## 从结果写出可核查的文章

按照 [数据分析](data-analysis.md) 重建汇总表，逐个回答初始研究问题。在工作记录里给每条主要结论留下一条可查路径，例如“摘要中的平均时延差 → 表 2 均匀负载行 → 汇总脚本的配对差 → 每条轨迹的原始行 → 对应配置与运行”。在新输出位置重新生成至少支撑中心结论的表或图。核对基线、方向、单位、舍入和独立重复数，再写入正文。[Sandve 等，可复现计算研究](https://doi.org/10.1371/journal.pcbi.1003285)

- **方法段**交代研究对象、候选及对照、可观测输入、比较预算、参数选择与正式评价的分界。说明代码在哪些输入上通过正确性检查。**结果段**先写效应及分布，再写失败、代价或没有优势的条件。为主要比较提供可复算的表或图，题注给出单位、样本和误差含义。
- **讨论与结论**分别回答“观察到什么”“哪条机制得到直接检验”“哪些解释仍可成立”。例如候选比 FIFO 快，但未超过相同搜索预算的随机策略，只能说观察到了所选策略相对 FIFO 的差异。判断两种选参方法的典型性能，要在匹配预算下独立重复整个搜索。将收益归因于某一个算子，还要在同样的搜索流程中移除或替换它，控制其他变化。结果为负时，按结果完成文章，并指出哪个原始假设失去支持。
- **正式成稿**按用户指定语言、格式和期刊组织题名、摘要、相关工作、方法、结果、讨论与结论。摘要、引言贡献和结论共用核准后的基线与范围。将科学问题讨论写进论文，将运行路径、复跑命令、版本、预算、失败或未测条件写到合适的方法段、附录或交付说明。按已有证据核查创新主张，并区分研究贡献与投稿等级适配。[NeurIPS 关于主张范围、限制和可复现性的问项](https://neurips.cc/public/guides/PaperChecklist)
- **完成条件**随委托而定。执行实验至少交付可重跑代码、运行及原始记录、分析和研究结论。要求“直接写成文章”时，还要给实际可读的论文稿并完成 [自然写作与文稿终检](natural-writing-and-review.md)。如果某项关键运行确实被环境阻挡，清楚注明已得证据能支撑的部分、待执行命令、所需用户操作和恢复位置。
